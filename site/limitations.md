This page lists what does not work yet, as far as it is known. It is updated as limitations are found and fixed.

## Compiler (all backends)

- **Java language level.** Java sources are parsed with a Java 20 grammar. Newer language features are not recognized.
- **Kotlin** support is experimental: only top-level class declarations are handled.
- The **Java backend** (ClassFile API) needs Java 24 or later to run.

## LLVM backend

### Building

- **Reflection, resources and proxies need configuration.** Classes that are only used through reflection, resources and dynamic proxies must be listed in GraalVM configuration files under `META-INF/native-image/` (see [the LLVM backend]({{ site.baseurl }}/backends/llvm/#reflection-resources-and-proxies)), as with GraalVM `native-image`. Otherwise classes are not compiled, resources are not found, and `Proxy.newProxyInstance` throws.
- **Slow builds, large executables.** The whole reachable part of the JDK is compiled and optimized: about 30 seconds and 13 MB for a small program, about 45 seconds and 15 MB for the [picocli example]({{ site.baseurl }}/examples/picocli-demo/), on an 8-core machine. LLVM's optimization and code generation run in parallel parts, so fewer cores means a slower build.
- **Incremental builds** with the LLVM backend gave correct executables in a test with two classes where each in turn was changed; larger programs have not been tried, and the examples build with `-Dnabu.incremental=false`.
- The build prints one summary line per kind of warning (for example about static fields of classes outside the compiled closure); the details are in `<name>.warnings.txt`. They do not stop the build, and most are harmless.

### Platforms

- **Windows x64 with MinGW-w64** is the only verified platform.
- **Linux** (Ubuntu on WSL2, gcc and `libgc-dev`, built with `-Djavacpp.platform=linux-x86_64`) runs the whole integration test suite (`ThreadsE2eIT` included). Stack traces have file and line numbers there too (read from the `.debug_line` section of the executable). macOS has not been tried; there the stack traces have no file and line numbers (the Mach-O format is not read).
- **macOS** (Apple Silicon) is tested only on a GitHub Actions runner (clang, `brew install bdw-gc`; the manual workflow `native-macos.yml`), not on a Mac of our own. There all of `ThreadsE2eIT` passes (70 of 71 tests; one is skipped because it needs the line tables), also with three test programs at once on the 3 cores of the runner (5 runs in a row). Stack traces have no file and line numbers (the Mach-O line tables are not read), and the frames of methods that LLVM inlined into another one are not shown separately. Virtual threads on continuations are **off by default** on macOS: set `NABU_CONTINUATIONS=1` to use them; otherwise every virtual thread gets a native thread.
- **MSVC** is not supported: the exception handling needs DWARF/LSDA unwind data, which the MSVC runtime does not provide.

### Run time

- **Threads run in parallel.** `new Thread(runnable).start()` creates a real native thread, and threads run at the same time on several cores (four threads that count primes take about a third of the time of one). `synchronized`, `volatile`, the atomic classes, the locks and `VarHandle` are atomic and ordered as the Java memory model says, and a class is initialized by one thread while the others wait for it. A thread that waits (`Thread.sleep`, `join`, `Object.wait`, `LockSupport.park`, a contended `synchronized`) is woken at once (about 90 microseconds for a hand-over between two threads). Every thread has a wake-up of its own, and a monitor or a class initializer has a queue of the threads that wait for it, so thousands of waiting threads cost next to nothing while they wait. The C parts of the class library guard their shared tables (types, `Class` objects, properties, symbols) and the cases where threads would disturb each other: positional reads and writes of a file channel (`read(dst, position)`) do not move the position of the channel, a file descriptor is closed once when two threads close it, and processes are started one at a time so that a child does not inherit the pipes of another start. Two threads that use the same stream, `RandomAccessFile` position or other object made by the C runtime at the same time are not protected beyond what the JDK code does. Set the environment variable `NABU_GIL=1` to run the threads one at a time again (a global lock handed over where a thread blocks); a loop that waits on a field that is not `volatile` may then never end, as on the JVM. Verified: a `Thread` subclass that overrides `run`, `start`, `join` (also with a `Duration`), `sleep`, `interrupt`, `wait`/`notify`, `synchronized`, a fixed `ExecutorService` with `Future`, `CompletableFuture`, `ForkJoinPool`, parallel streams and `java.util.Timer`, `Thread.setUncaughtExceptionHandler` / `setDefaultUncaughtExceptionHandler`, thread groups, the `java.util.concurrent` locks and synchronizers (`ReentrantLock`, `ReentrantReadWriteLock`, `StampedLock`, `Semaphore`, `CountDownLatch`, `CyclicBarrier`, `Phaser`, `Exchanger`), the blocking queues (`ArrayBlockingQueue`, `SynchronousQueue`, `LinkedTransferQueue`, `DelayQueue`), `ScheduledExecutorService`, `ConcurrentHashMap` and the atomic arrays used from several threads, and virtual threads (`Thread.ofVirtual()`, `Thread.startVirtualThread`, `Executors.newVirtualThreadPerTaskExecutor()`). `Thread.getState()` tells `TIMED_WAITING` (`sleep`, a timed `wait`, `parkNanos`), `WAITING` (`wait`, `join`, `park`) and `BLOCKED` (a contended `synchronized`), `Thread.holdsLock` is exact, and a `InheritableThreadLocal` is copied to the threads that are made from a thread that has one. `Thread.getStackTrace()` of another thread and `Thread.getAllStackTraces()` give the stack of a thread that waits (`sleep`, `join`, `wait`, `park`, a monitor), spins on a volatile field, or computes in a loop: every jump back of a loop and the start of every function that calls others looks at a flag, so the thread answers at its next iteration or call (also in deep recursion). A thread that runs for more than 200 ms inside one function that neither loops nor calls (for example one long C call such as a big `memcpy`) does not answer, and its trace is empty, as the trace of a thread that has not started or has ended. Also verified: `invokeAll`, `invokeAny`, `ExecutorCompletionService`, `LinkedBlockingQueue`, thread factories and `shutdownNow` (which interrupts the running tasks). At the end of `main` the program waits for the threads that are not daemons, unless `System.exit` was called. An exception that escapes `run` goes to the handler of the thread, else to the default handler, else it is printed as `Exception in thread "name" …`; it ends that thread only.
- **Virtual threads run on continuations with the Boehm collector, on Windows (fibers) and Linux (ucontext, x86-64 and aarch64; tested on x86-64 under WSL).** A virtual thread has a stack of its own (a fiber) that is mounted on a pool of carrier threads, as on a JVM, so sleeping or parked virtual threads do not hold a native thread (20000 virtual threads that sleep for a second take about 1.6 s, 2 times faster than on native threads). A virtual thread that waits in `Object.wait`, sleeps or parks inside a `synchronized` block does not keep its carrier either: the monitor stays owned by the virtual thread. A virtual thread that has to wait for a monitor does not keep its carrier: it queues up for the monitor and parks, and the release of the monitor unparks the first in the queue. Only a virtual thread inside a critical section of the JDK (`Continuation.pin`) or with `NABU_CONTINUATIONS=0` keeps its carrier. `getStackTrace()` of a virtual thread that is parked gives its frames (the continuation walks its own stack); as everywhere, frames that LLVM inlined are merged into the frame they were inlined into. Set the environment variable `NABU_CONTINUATIONS=0` to bind every virtual thread to a native thread of its own (as on a JVM without continuation support), which is also what happens on macOS and with the other garbage collectors: a program with many thousands of them then uses that many native threads. With `NABU_CONTINUATIONS=0` a virtual thread gets a stack of 4 MB (a platform thread 16 MB). On Windows a stack is reserved and its pages are committed when they are used, so a virtual thread that waits costs about 40 KB: 20000 virtual threads that sleep at the same time take about 800 MB and work. Deep recursion in a virtual thread overflows sooner than in a platform thread. On continuations a parked virtual thread costs about 8 KB of memory on Linux (100000 take 0.8 GB on Windows, 500000 about 4 GB on Linux), because the 4 MB stack is only reserved and its pages are committed when they are used. On Linux every stack is two memory mappings, so the limit on mappings of the system (`vm.max_map_count`, 65530 by default) allows about 30000 parked virtual threads; the next one gets an `OutOfMemoryError` and a message on stderr that names the setting (raise it with `sysctl vm.max_map_count=262144` for more). A virtual thread that is parked for good (nobody will unpark it) is collected once nothing refers to it any more, if you set the system property `jdk.trackAllThreads` to `false` before the first virtual thread starts (`System.setProperty`); by default the JDK keeps every virtual thread in the root thread container, on a JVM too, and none is collected. Then its stack is only scanned while the continuation is reachable, and a finalizer gives the stack back (200000 abandoned virtual threads do not run into the mapping limit: when it is reached a collection runs first). A virtual thread that waits in `Object.wait` or for a monitor stays alive, because the wait queues keep a reference to it. Virtual threads are daemons, are named "" unless you name them, and are in the group `VirtualThreads`. `Thread.interrupt()` also wakes a platform thread that is blocked in a read of a `FileChannel` (a FIFO, a terminal): the channel is closed and the read fails with `ClosedByInterruptException`, as on a JVM. This works on Linux (a signal wakes the blocked thread) and on Windows (`CancelSynchronousIo` ends the read). As on a JVM, a virtual thread that is blocked in such a read is not woken: the interrupt closes the channel, but the read ends only when the data arrives. `synchronized` methods hold the monitor of `this` (of the class, when static), in your code and in the JDK. `ThreadLocal` and `ScopedValue` work (a virtual thread does not inherit bindings); `StructuredTaskScope` (a preview API) works with the default joiner: forked subtasks run in virtual threads, `join` waits for them, a failing subtask makes `join` throw `FailedException`, and subtasks see the scoped values of the thread that opened the scope. `Joiner.anySuccessfulResultOrThrow` (which cancels the other subtasks: a subtask that sleeps is interrupted), `Joiner.allSuccessfulOrThrow` and `Joiner.awaitAll` work, and `Subtask.state()` reports the outcome. A scope with a timeout works.
- **Thread groups** form a tree (`system` > `main` > your groups) with `getParent`, `parentOf`, `activeCount`, `activeGroupCount` and `enumerate`; the groups are kept for the whole run, even when nothing refers to them. `interrupt` and `setMaxPriority` act on the whole subtree; `destroy` does nothing, as on current JVMs; `list()` prints the group, its threads and its subgroups. `Thread.toString()` gives `Thread[#id,name,priority,group]`. A thread that has ended has no group (`getThreadGroup()` is `null`), as on the JVM.
- **Casts are checked as far as the runtime can tell**: a wrong `(Integer) object`, a cast to an interface of the program or a cast to an array type throws `ClassCastException`. A cast passes unchecked when the object was made by the C runtime or the target is a JDK interface that the program does not contain. Array indexes and integer division by zero are checked.
- **The JDK is only covered as far as it has been tried.** What runs: collections, streams, `String.format`, regex, `java.time` (including `LocalDate.now()`), `BigInteger` and `BigDecimal`, `Random`, `SecureRandom` and `UUID`, `MessageDigest` (MD5, SHA-1, SHA-2), `Mac` (HMAC), RSA key pairs and `SHA256withRSA` signatures, `ConcurrentLinkedQueue`, `ConcurrentLinkedDeque`, `ConcurrentSkipListMap` and the atomic classes (also used from several threads at once), `Cipher` (AES with CBC, ECB, CTR or GCM), `KeyGenerator` and `SecretKeyFactory` (PBKDF2) from the SunJCE provider (no jar verification of providers: all providers are trusted), `CRC32`, `Base64`, `Properties`, `URI`, `DecimalFormat`, `SimpleDateFormat` and the common `Files` methods (including `walk`, `walkFileTree`, `list`, `newDirectoryStream`, `copy`, `move`, `readAttributes` with basic and DOS attributes, `setLastModifiedTime`, `getFileStore`, `toRealPath` and `probeContentType`, which goes by the file extension), `RandomAccessFile`, file channels (`FileChannel.open`, `Files.newByteChannel`, `getChannel()`, direct buffers; no memory mapping, no file locks between processes, direct buffers are freed only by `Cleaner` runs, which do not happen) and `ProcessBuilder`/`Runtime.exec` (the redirects `PIPE` and `INHERIT`, no file redirects, no `onExit`). What does not: serialization (`ObjectOutputStream`), other ciphers, other signature algorithms than RSA, and key stores, and other file attributes (POSIX permissions, ACLs, symbolic links; `getOwner` only gives the name of the user running the program). Other parts of the JDK have not been tried. Only the locale data of the root locale is included, so formatting and display names follow English conventions.
- **`lib/tzdb.dat`** is copied next to the executable at build time. The time zone database is read from there, so ship the `lib` directory with the executable. The default time zone comes from the `TZ` variable or from the Windows zone (a table of common zones); otherwise it is UTC.
- **`SecureRandom`** uses the random bytes of the operating system; the algorithm name is not one of the JDK's.
- **Native and VM-internal JDK methods** have no implementation unless the C runtime provides one. A program that calls such a method stops with `nabu: call to a JDK function without an implementation: <name>` and exit code 127. All such methods are listed, grouped by class, in `<name>.unresolved.txt` at build time.
- **Reflection** only covers classes and members listed in GraalVM `*-config.json` metadata (in the class output directory or in jars on the classpath). Fields, methods, constructors, generic types and annotations of those are available; a member that is not registered is not found (`NoSuchMethodException`).
- **Static fields of classes outside the compiled closure** keep their default value (`0`/`null`); the build lists them in `<name>.warnings.txt`.
- **Stack traces are approximate.** `getStackTrace()` and `printStackTrace()` list the methods, found from the symbol table of the executable, with file and line for code compiled from your sources (`at Main.run(Main.java:12)`). JDK and library methods have no line numbers (`Unknown Source`). Methods that LLVM inlined are frames of the trace too, with the line of the call (the debug info of the executable names them; the executable is some 10 to 15 percent larger for it), and a stripped executable has no trace. An exception that reaches the top of the program prints `Exception in thread "main"` and its trace and exits with code 1. See [Troubleshooting]({{ site.baseurl }}/backends/llvm/troubleshooting/).
- **Garbage collection:** only `--gc=BOEHM` (the default) is suitable for executables. `NONE` allocates objects on the stack, so they are invalid once the creating function returns.
- The VM-bound parts of the class library (`Class`, `System`, `Thread`, `Runtime`, reflection, `Unsafe`) are implemented in C (`runtime/jcl_lite.c`) instead of compiled from the JDK. They can behave differently from the JDK in edge cases.
- **Unclosed file streams** are only closed when the garbage collector finds them unreachable (`--gc=BOEHM`), which can take a while. Until then the file stays locked on Windows, so close your streams.
